# PLAN_01 — Workflow Editor MVP (Frontend)

> **Branch**: `Frontend` · **Authored**: 2026-04-21 · **Status**: Draft
>
> The first PLAN for the Frontend brand. Builds a React Flow-based
> workflow editor so users can drag nodes from the palette onto the
> canvas, connect them with edges, and run them end-to-end. The AI
> Composer layer (PLAN_02) is injected on top of this editor, so the
> canvas / property-edit / save paths must stabilize first before
> anything else can be stacked on them.

## 1. Goals

1. Scaffold a Next.js 14 (App Router) + TypeScript Frontend project
2. Node palette (left sidebar) — browse the full `Execution_Engine/src/nodes/` catalog
3. Canvas (React Flow) — drag-and-drop placement · edge connection · visual feedback for cycle prevention
4. Property panel (right) — edit the selected node's config (dynamic form generated from a per-node schema)
5. Workflow save/load — wired to `POST/GET/PUT /api/v1/workflows`
6. Manual execution — `POST /api/v1/workflows/{id}/execute` + polling display of the result
7. Single-user-token dev mode — use the API token from `.env.local` directly

## 3. Node catalog sync strategy

The frontend has to know the list of nodes in `Execution_Engine/src/nodes/`
and each node's config schema. **Two options**:

| Option | Description | Trade-off |
|------|------|-------------|
| A. Runtime fetch | Add a `GET /api/v1/nodes/catalog` endpoint (API_Server) → deserialize the registry | Adds 1 backend endpoint. Frontend does not change when nodes are added |
| B. Build-time injection | Dump the backend `registry` to JSON and bundle it at Frontend build time | Adding a node forces a Frontend rebuild. In exchange, no runtime dependency |

**Adopted: A** — nodes are expanding quickly right now, so the runtime
fetch is more flexible. Each node returns
`{name, category, display_name, description, config_schema}`. The
`config_schema` is JSON Schema, which the Frontend `PropertyPanel`
consumes to render a dynamic form.

**Prerequisite**: add `app/routers/node_catalog.py` on the API_Server.
Included in this PLAN, but merge the API_Server PR first, then wire up
the Frontend.

## 5. Canvas behavior spec

- **Drag-and-drop**: dropping from the palette onto the canvas invokes the `addNode(type, position)` Zustand action
- **Edge connection**: the React Flow `onConnect` hook records `source_handle`, `target_handle`
- **Validation**: before saving, run client-side logic equivalent to `dag_validator` (cycles/orphan nodes). The server-side check is the source of truth, but this gives UX feedback
- **Auto layout**: an `Auto Layout` button driven by `dagre` (required for laying out DAGs generated by the AI Composer, so include in MVP)
- **Undo/Redo**: Zustand middleware (`zundo`) — included in MVP (essential editor UX)

## 6. Property panel dynamic form

- Selecting a node renders a form in the right panel based on `config_schema`
- JSON Schema → React component mapping: evaluate `@rjsf/core` (React JSON Schema Form) vs. writing a mapper by hand
  - **Adopted: hand-written mapper** (supports only 5 basic types: string / number / boolean / enum / secret_ref). `@rjsf` has high style-customization cost
- `secret_ref` fields are dropdowns (the user's Credentials list) — **however, since the Credentials UI is PLAN_07**, the MVP allows manual entry (free-text credential_id)

## 7. API wiring

| Action | Endpoint | Method |
|------|-----------|--------|
| Node catalog | `/api/v1/nodes/catalog` | GET |
| Workflow list | `/api/v1/workflows` | GET |
| Workflow read | `/api/v1/workflows/{id}` | GET |
| Create | `/api/v1/workflows` | POST |
| Update | `/api/v1/workflows/{id}` | PUT |
| Execute | `/api/v1/workflows/{id}/execute` | POST |
| Execution result | `/api/v1/executions/{exec_id}` | GET (polling) |
